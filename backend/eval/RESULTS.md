# Extraction accuracy

Field-level accuracy of the receipt-extraction pipeline over a hand-labelled set of **11** real Portuguese receipts (multi-rate VAT, rotated photos, discounts, and a payment-only receipt). Generated by `backend/scripts/eval_extraction.py`.

- **Provider / model:** openai · `gpt-5-mini`
- **Run date:** 2026-10-19
- **Scored:** the user-facing fields after the deterministic VAT / amount / category logic (not just the raw LLM JSON).

| Field | Accuracy | Correct / scored |
|---|---:|---:|
| vendor | 100.0% | 11/11 |
| date | 90.9% | 10/11 |
| total | 100.0% | 11/11 |
| vat_amount | 100.0% | 9/9 |

> Notes: `total` is the amount paid after discounts; `vat_amount`/`vat_rate` are scored only on receipts that print a VAT table (dominant rate for the single-rate column); vendor matching is fuzzy (merchant or payment processor).

## Guardrail effectiveness

Does the review gate actually catch the reads that are wrong? Measured by running the shipped gate (`services/gating.decide_gate`) over the same set and comparing its decision against whether each read was actually correct.

| Metric | Value | |
|---|---:|---|
| Wrong reads caught by the gate | **0%** | 0/1 wrong reads routed to review |
| False auto-posts | **1** | a wrong read that still auto-posted (100% of wrong reads) |
| Over-review | 70% | correct reads sent to review anyway (7/10) — friction, not risk |
